**F-M3 — MEDIUM — The whole-package rule's stated monotonicity is false for an identity that the enriching package itself introduces; the code over-refuses, blaming the recorded ENRICH.** *(Re-opens the documentary gloss on the accepted invariant, not the invariant.)*
Claim under test: FoundryRegistry.java:727-731 ("order-independent … attributable … and monotone (later admissions can only add to the other variants, never invalidate a recorded enrichment)"), ADR-0007:33-37 ("order-independent, attributable and monotone … an enrichment never causes it"), ADR-0007:225 ("refusing … would let any later plain admission retroactively invalidate a recorded enrichment").
Mechanism: `knownOutside` (FoundryRegistry.java:1049-1058) returns true when the other identity has no occurrence outside the enriching package (:1052). An enriching package may therefore introduce a *new* identity C (also allowed by `enrich()` preflight at :882). Once any other package carries a different variant of C, `others` is non-empty, C0 is not in it, C has no ENRICH chain, so `enforceWholePackageRule` (:747-761) refuses the recorded ENRICH of A.
Probe J (ran): t0 = A0/B0 registered; `enrich(A1+B0+C0, A)` accepted, `verify()` passes, 3 identities. Then `register(A1+B0+C1')` (C re-worded, A and B verbatim) → **REFUSED**: "ENRICH idop-28ba… refused: package pkg-2bcd… introduces a new variant of uao-c41c… (fixture:biology:dairy-cattle)". The same three packages registered plainly with no ENRICH → accepted, C = MULTIPLE_UNRECONCILED_VARIANTS (the registry's admission law permits it). Hand-placing the divergent package into `packages/` → `index()` fails closed and `verify()` fails with the same message, i.e. a registry rebuilt from its two stores with that set is unreadable.
Assessment: the implementation faithfully computes the accepted set-based invariant ("introduces no new variant of any other registered identity" — in the final set C is registered and C0 exists nowhere else), and it fails closed, so no wrong state is ever admitted. But (i) the monotonicity property as written in the code, the ADR Decision and the tenth-remediation entry is false; (ii) a legitimate plain admission is permanently refused for any identity first introduced through an enrichment, until some other package restates that identity's first variant verbatim (then :1053 admits it — I traced this, did not run it); (iii) the refusal names the ENRICH and its package as the culprit when the divergence is the plain package's. Enriching packages routinely introduce new identities (`build_enrichment_bundle.py:8-9` keeps "new identities and relationship candidates"), so this will be met in operation. Given that no set-based rule can distinguish this case from the one it must refuse (enriching package introduces a divergent C0 after a plain C1 existed), fail-closed is defensible — but it must be stated honestly.
Condition M-1: correct FoundryRegistry.java:727-731 and ADR-0007:33-37 / :225 to state the actual property (order-independent and attributable; monotone only for identities that exist outside the enriching package; an identity the enriching package introduces is pinned to that state until it is restated elsewhere or enriched itself); make the refusal name both packages; add a test pinning probe J's outcome. If the founder judges the pin unacceptable, that is a rule change and needs another pass.
